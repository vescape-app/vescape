# Tune profiles are scoped by Refloat package version

Tune Profiles are retained per Board but are only shown and used within the same normalized base Refloat package version they were created from. Refloat releases can change field meaning and expected rider behavior enough that cross-version tune migration would require hidden conversion tables and long-term maintenance, so the app keeps older-version profiles for rollback/reflash scenarios but does not apply them to the current board state. Suffixes and fork labels such as preview or board-specific builds are kept in the exact firmware identity for link integrity, but they do not split Tune Profile compatibility buckets. Legacy Refloat info v1 reports two-part versions such as `1.1`; those exact two-part versions form compatibility buckets alongside the three-part versions reported by info v2.

When a trusted board read finds no Tune Profile for the current Refloat package version, the app waits for an explicit rider action such as "Create tune based on board config" before creating the first profile from the board. Tune writes remain read-before-write and schema-validated as described in [ADR 0001](./0001-tune-profile-storage-and-sync.md), but Refloat-version compatibility gates which profiles can be selected or pushed.
