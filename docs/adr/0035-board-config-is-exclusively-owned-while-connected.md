# Board config is mandatory link state and exclusively owned while connected

Refloat config values serve config-scoped Board Warnings, live footpad engagement, Tune prefill and writes, and VESC-relative Alerts. Treating their durable copy as an optional cache leaves every consumer with a fallback path and lets a valid Board Link exist without the config state needed to interpret the Board. Decided: a Board Probe must read and decode the whole config and persist **Last Known Board Config Values** before it may save the Board Link. Failure fails linking, and the Board Link version is bumped so existing links re-link into the same invariant instead of becoming a permanent optional case.

The persisted state is **Last Known Board Config Values**, not a cache: one durable latest field map per Board and Refloat base version (the Tune Compatibility boundary from ADR 0022). It is read-side truth immediately available when a Board Session starts, including for footpad thresholds and VESC-relative Alerts. It is never a write base because another tool could have changed the Board while Vescape was disconnected. A mismatched Link Integrity Check clears it because field offsets are meaningless against different firmware; an outdated link keeps it until re-link.

Each trusted Board Session still reads the whole config once and refreshes after Vescape's own writes. A fresh object carries both the decoded field map and the raw config bytes, package signature and parsed schema. Only those current-session bytes may back a write, since writes patch the original blob rather than re-encoding a map. A Board accepts one BLE central at a time, so while the session continuously owns the link, its fresh bytes remain authoritative and the Tune path need not defensively re-read before every write. A disconnected interval demotes the values back to last-known read-side state until the next fresh read. A rider writing over CAN from another controller can still desync the session; defending that expert case would tax every rider with repeated reads and remains out of scope.

VESC-relative Alerts persist a config field relationship and lead offset, never a copied threshold. Native alert evaluation resolves the relationship from Last Known Board Config Values immediately on connection and follows the fresh value automatically when it arrives, without JS regeneration. The first slice is opt-in Duty feedback based on `tiltback_duty`: matching defaults off, while Safe, Normal and Minimal choose how far feedback begins below the VESC threshold. Other voltage, BMS and current relationships remain future work because their units and semantics differ.

A fresh read that differs from Last Known Board Config Values and was not caused by Vescape creates a **Board Config Change Notice** containing every changed field. It is informational, not a Board Warning: a deliberate LED or tune change is not an abnormal Board condition. Only the latest transition per Board is retained, only the active Board presents it, and dismissing the one-button modal by any route deletes it. The pending notice is durable only so a background read cannot update Last Known Board Config Values and lose the rider notification before JS becomes available; no acknowledgement record or change history remains afterward.

JS reads the decoded field map through a dedicated accessor and change event, not through Live State: the map is schema-wide, changes rarely, and does not belong on the hot event that recomposes for phase, GPS and scans. Raw config bytes and package signatures remain native.
