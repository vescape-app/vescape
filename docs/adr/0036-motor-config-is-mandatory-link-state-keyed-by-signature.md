# Motor config is mandatory link state keyed by its serialization signature

Refloat config is mandatory link state (ADR 0035) because the board serves its own settings XML: whatever firmware is in front of us, its schema arrives with it, so the config is always decodable and a failure to read one is a real fault. `COMM_GET_MCCONF` has no such property. It returns a bare serialized blob and VESC ships no schema for it, so the offsets must come from a layout the app carries. That difference matters for _how_ the config is resolved, but not for how much we commit to it: **Motor Config Values are mandatory link state**, exactly like Refloat config. The Board Probe reads MCCONF over the same throwaway Board Session, after the Refloat read, and a link is not offered unless it decodes.

This was first specified the other way — optional, linking succeeds without it — on the reasoning that a missing section on two control screens beats refusing to link a board whose firmware we have not tabulated. That reasoning was rejected in favour of failing fast. Both configs behave identically now: read at link time, shown as their own timeline row, and a failure aborts the link rather than degrading silently. The cost is real and worth stating plainly — a board running firmware whose signature no layout carries **cannot be linked at all** until its table is generated, and Floatwheel firmware is the most likely case to hit it. The benefit is that every Board Link carries the same guarantees, and a board that would silently lose temperature cutoffs, VESC-relative alerts and motor config display announces that at link time instead of at ride time.

Resolution is by **MCCONF signature** — the leading `uint32` of the blob, which VESC's code generator derives from the parameter set and which firmware's own reader rejects on mismatch. Firmware version is not the key: the same `FW 6.05` string ships different layouts across hardware variants and vendor forks, and a version match that is not a layout match decodes confidently wrong values. The signature is exact or it is nothing; there is no nearest-match, no prefix-length heuristic, and no plausibility check on decoded values. A board whose signature we do not carry fails linking with `PROBE_MOTOR_CONFIG_TIMEOUT` and reports that signature in the log alongside firmware version and hardware name, so a table can be generated for it. Verified on a Thor301: signature `1065524471`, stock `release_6_05` layout, every decoded field matching VESC Tool.

Layouts are **generated from firmware's `confgenerator_serialize_mcconf`, never hand-written and never derived from VESC Tool's parameter XML**. The XML describes editor metadata — decimals, min/max, suffix — and disagrees with the wire format: it declares the temperature cutoffs as scaled `float16` where firmware writes single bytes. Worse, a field can hold its offset across versions while changing its type, so an offset-only check passes and yields garbage. The serializer is the only authority. We tabulate whole layouts rather than the version-invariant prefix, because the fields worth having — speed calibration (`si_*`), motor temperature sensor type, BMS limits, FOC parameters — lie past the prefix, and generating a full table costs no more than generating a partial one. Tables are committed as generated source per platform under `@parity`, not parsed from a bundled asset at runtime: we own the data, the parse would be dead weight, and typed tables let a missing signature be a compile-time-shaped absence rather than a runtime one.

The read is **read-only, permanently**. Motor config writes are out of scope regardless of how complete our tables become; a bad motor configuration damages hardware, and none of the rider-facing value here requires writing. Persistence follows the Last Known Board Config Values pattern of ADR 0035 — one durable latest field map per Board, keyed by signature instead of Refloat base version, read-side truth available when a Board Session starts, cleared by a mismatched Link Integrity Check. This is what lets VESC-relative Alerts extend past `tiltback_duty` to `l_temp_fet_start` and `l_temp_motor_start`, closing a real rider confusion: firmware temperature derating feels exactly like Refloat pushback, and Refloat has no temperature parameter at all, so riders attribute it to a tune that cannot produce it. Consequence worth knowing: every new firmware release blocks linking until someone regenerates its table. That is deliberate under the fail-fast rule above — a silent wrong temperature is worse than an absent one, and an absent one is worse than an honest refusal — but it makes table coverage a release-blocking concern rather than a nice-to-have.
