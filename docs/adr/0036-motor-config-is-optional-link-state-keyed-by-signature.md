# Motor config is optional link state keyed by its serialization signature

Refloat config is mandatory link state (ADR 0035) because the board serves its own settings XML: whatever firmware is in front of us, its schema arrives with it, so the config is always decodable and a failure to read one is a real fault. `COMM_GET_MCCONF` has no such property. It returns a bare serialized blob and VESC ships no schema for it, so the offsets must come from a layout the app carries. That difference in where the schema comes from is what forces a different invariant, not a weaker commitment: **Motor Config Values are optional link state**. An unrecognized serialization means no motor config, and linking succeeds anyway. Making it mandatory would fail linking on firmware we simply have not tabulated yet, which is a worse outcome than a missing section on two control screens.

Resolution is by **MCCONF signature** — the leading `uint32` of the blob, which VESC's code generator derives from the parameter set and which firmware's own reader rejects on mismatch. Firmware version is not the key: the same `FW 6.05` string ships different layouts across hardware variants and vendor forks, and a version match that is not a layout match decodes confidently wrong values. The signature is exact or it is nothing; there is no nearest-match, no prefix-length heuristic, and no plausibility check on decoded values. A board whose signature we do not carry reports that signature alongside firmware version and hardware name, and shows no motor config. Verified on a Thor301: signature `1065524471`, stock `release_6_05` layout, every decoded field matching VESC Tool.

Layouts are **generated from firmware's `confgenerator_serialize_mcconf`, never hand-written and never derived from VESC Tool's parameter XML**. The XML describes editor metadata — decimals, min/max, suffix — and disagrees with the wire format: it declares the temperature cutoffs as scaled `float16` where firmware writes single bytes. Worse, a field can hold its offset across versions while changing its type, so an offset-only check passes and yields garbage. The serializer is the only authority. We tabulate whole layouts rather than the version-invariant prefix, because the fields worth having — speed calibration (`si_*`), motor temperature sensor type, BMS limits, FOC parameters — lie past the prefix, and generating a full table costs no more than generating a partial one. Tables are committed as generated source per platform under `@parity`, not parsed from a bundled asset at runtime: we own the data, the parse would be dead weight, and typed tables let a missing signature be a compile-time-shaped absence rather than a runtime one.

The read is **read-only, permanently**. Motor config writes are out of scope regardless of how complete our tables become; a bad motor configuration damages hardware, and none of the rider-facing value here requires writing. Persistence follows the Last Known Board Config Values pattern of ADR 0035 — one durable latest field map per Board, keyed by signature instead of Refloat base version, read-side truth available when a Board Session starts, cleared by a mismatched Link Integrity Check. This is what lets VESC-relative Alerts extend past `tiltback_duty` to `l_temp_fet_start` and `l_temp_motor_start`, closing a real rider confusion: firmware temperature derating feels exactly like Refloat pushback, and Refloat has no temperature parameter at all, so riders attribute it to a tune that cannot produce it. Consequence worth knowing: every new firmware release is invisible to this feature until someone regenerates its table, and that is deliberate — a silent wrong temperature is worse than an absent one.
