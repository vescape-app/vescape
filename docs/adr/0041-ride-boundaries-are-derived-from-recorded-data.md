# Ride boundaries are derived from recorded data

ADR-0038 gave every Ride Recording a durable identity and explicit start/end boundaries in
`ride_recordings`, with `recording_id` on frames, Ride Track points and minute buckets. An end time
is only right if the process is alive to write it, so a launch sweep patched abandoned rows from the
last frame and fix. The real end always came from the data, and the column was a cache that could
be wrong. It also left two grouping paths: identified rides grouped on `recording_id`, older rides on
Board + time gap + break markers. App kill, auto close and a quick reconnect split rides that should
be one, while a two-hour stop while connected stayed one ride with a two-hour hole.

We decided that ride boundaries are derived from the recorded data only. This reverses the
"Recording identity and history boundaries" part of ADR-0038. The Ride Track as a separate durable
GPS stream stands.

## Status

Accepted. Supersedes the recording-identity part of ADR-0038.

## Decision

- **A ride is one Board's Telemetry Samples.** A new ride starts when the Board changes, when the
  gap between consecutive Telemetry Samples exceeds the rider's `rideSplitGapMinutes` (default 30),
  or at an explicit **Stop Recording**.
- **Frames are the evidence.** Idle Pause halts frame writes on the first disengaged Refloat sample,
  so every stored frame means the board was engaged. Indoor GPS jumps and carrying the board write
  no frames and cannot move a boundary.
- **GPS never starts or extends a ride on its own.** A GPS-only minute bucket attaches to the
  preceding ride of its Board, within the split window and before any Stop Recording. In practice
  that is the Ride Dropout Grace tail after the last frame. Route, scrubber and Moving Window still
  read the Ride Track as before.
- **Stop Recording is the only marker that splits.** It writes its own `recording_stop` marker,
  distinct from the `app_stop` an ordinary Board Session stop writes. `disconnected`, `error`,
  `connection_lost` and `app_stop` stay as Ride History Markers but no longer split. Disconnect, app
  kill, auto close, BLE loss, Idle Pause and process restart need no handling.
- **One grouping path** for every ride, old and new. Range reads (export, selection, deletion,
  media matching, route preview, track projection) use Board and time only.
- **Schema v52** drops `ride_recordings` and every `recording_id` column, and returns the bucket key
  to `(bucket_start_ms, board_id)`. Two recordings of one Board that shared a minute fold into one
  bucket; the folded minute's route preview is regenerated by history maintenance. Legacy fixes
  without reported accuracy read as precise only through their missing recording id, so the
  migration stamps them with the 20 m precision threshold.

## Considered Options

- **Keep `ride_recordings` and fix the sweep.** Rejected: the end would still be a cache of the
  data, and every new lifecycle path (restoration, Board change, storage failure) needs its own
  close rule.
- **Split on disconnect markers too.** Rejected: a bar stop with the app killed is one ride to the
  rider.
- **Let GPS-only minutes extend a ride.** Rejected: GPS jitter indoors or a walk home would keep a
  ride open or create phantom rides.

## Consequences

- Boards without Refloat state (legacy Float) record frames while standing, so a long stop while
  connected stays one ride for them. Accepted for now.
- A Stop Recording and a restart inside the same minute bucket cannot split, because boundaries have
  minute-bucket resolution.
- Old `app_stop` markers from a past Stop Recording are indistinguishable from a session stop and no
  longer split those rides; they regroup on the frame gap.
- Stop Recording, and with it the `recording_stop` trigger, is expected to be removed later.
